Measured quirks (each is a line of an oracle, and the port reproduces it):
- File loaders read the file into the shared 10 MiB `SliceY.SliceBuffer` and `limit(n)` it. A `GameWindow.ReadString(ByteBuffer)` whose count runs past the limit reads whatever the buffer held beyond the data, so a truncated `map_symbols.bin` symbol string or `gos_*.bin` payload gives a result that depends on the buffer's earlier use. The probes zero the buffer before such loads and the port models it as zeros (`ByteBuffer::wrap_slice_buffer`); a count that passes the buffer's capacity is the original's `IllegalArgumentException: newLimit > capacity: (P > C)` (`StringUTF.load`'s `limit()` call). UNKNOWN: what a real session's stale bytes would be (the live game never starts a load on a zeroed buffer).
- `KahluaTable.load` empties the table first and keeps every entry read before a failure; `WorldMapSymbols.load` appends one symbol at a time and keeps the earlier ones when a later one fails (a bad type or texture string ends the list there).
- `WorldMapVisited`: flags passed to `setFlags`/`clearFlags` are not masked and the unit arithmetic is on signed bytes, so a flag value with bits above the unit's two spills into the higher units of the same byte (or is cut off at the byte's end) exactly as in the original; the legacy format's rows are read through one buffer, so a short row keeps the previous row's tail.
- `IsoRegions`: `DataChunk.load` activates levels from `min(highestZ, 31)` down to 0 (`ensureSquares` ignores 32 and above) but keeps the file's `highestZ` (`hz=32` and `hz=40` print as read); a byte count that is smaller or larger than the flag array fails only past the end of the array (the bytes before it are kept). A chunk file whose length field is 3000 or -4 stops the whole load after the discovery list got its id (`disc=[...]`, no chunk). A header that names chunks without a file makes the original warn and throw `IsoRegionException` ("previously discovered chunks have not been loaded") after the files were queued, and the loaded chunks stay.
- `ErosionConfig.readFile` splits each line with `split("=")`: `a = ` gives two pieces (`"a "` and `" "`), so an empty value fails `Integer.parseInt` (the read stops with false and keeps what was read before), while `a =` gives one piece and is only logged as unknown; `a = 5=` is a valid line (trailing empty pieces are dropped), `a = 1 = 2` is unknown. `debug.enabled` is `Boolean.parseBoolean` (`tRuE` is true, `yes` is false); a UTF-8 BOM in front of a key is not removed by `trim()`, so that key is unknown; invalid UTF-8 inside a value fails the number.
- `IsoWorld.readWorldVersion` reads `map_t.bin`'s `GMTM` magic on a server and `map_ver.bin`'s first int otherwise (-1 for a missing, short or foreign file); `GameWindow.ReadString(DataInputStream)` returns `""` for length 0, throws `RuntimeException` over 65536 and `NegativeArraySizeException` for a negative length (`new StringBuilder(len)`), then reads that many UTF-16 chars.

How the probes get the cases the real save does not have: the gos, savemeta and isoregion writers are the ORIGINAL classes (`SGlobalObjectSystem.save`, `WorldGenParams.save`, `MapItem.SaveWorldMap`, `StatisticsManager.save`, `Helicopter.save`, `JobChunkUpdate.addChunkFromDataChunk` + `saveChunksToDisk`), and `map_visited.bin` is made by the original's own `save()` (4 MB, so only the commands are committed). Probe-side shortcuts that are not the original's code path: `MapVerProbe` switches `GameServer.server` off for the length of one `readWorldVersion` call and repeats the three lines `IsoWorld.init` runs on `map_ver.bin` (`init` cannot run on a server); `IsoRegionProbe` constructs an `IsoRegionWorker` without starting its thread and runs the queued `ChunkUpdate` jobs through `JobChunkUpdate.readChunksPacket` itself, with the job pool emptied and the worker's static 2076 byte buffer zeroed first (a pooled job keeps the stale bytes of an earlier one); the chunk files are handed to the port in file-name order, while the original lists the directory in file-system order (every multi-file scenario loads all files without a failure, and the discovery list is printed sorted).

Ported: `zombie.globalObjects` (`SGlobalObjects`, `SGlobalObjectSystem` load, `GlobalObjectLookup`), `KahluaTable.load` (`load_into`), `zombie.statistics` (`StatisticsManager`, `Statistic`, `StatisticType`, `StatisticCategory`, `Achievement`), `zombie.iso.MetaTracker` (`Helicopter.load` on the server, `Alarm`, `AmbientStreamManager.load`), `WorldGenParams.load`, `WorldMapSymbols.load` and `MapItem.LoadWorldMap`, `WorldMapVisited` (grid, mutators, `save`, `load` with the legacy format), `zombie.iso.areas.isoregion` (`IsoRegions.hash`, `DataChunk`, `DataRoot` select/get, `JobChunkUpdate`, `IsoRegionWorker.loadSaveMap`), `zombie.erosion.ErosionConfig` (fields, `readFile`, `writeFile`), `IsoWorld.readWorldVersion` and the `map_ver.bin` read (`zombie/iso/world_version.rs`). `ByteBuffer` (`java_nio.rs`) now has a capacity and `GameWindow.ReadString(ByteBuffer)`'s behaviour past the limit.

UNKNOWN / not ported:

- The port's `java::parse_int` rejects the non-ASCII digits `Integer.parseInt` accepts, and `java::parse_double`/`parse_float` reject hex floats (`0x1p3`); the `erosionini` oracle does not exercise them (UNKNOWN). A Java string holding an unpaired surrogate (a `map_ver.bin` map list written with one) comes out of the port with U+FFFD, since a Rust `String` cannot hold it (that case was left out of `mapver`).
- The speed scaling `ErosionMain.initConfig` applies after reading `erosion.ini`, `ErosionConfig`'s network `save`/`load` (`ByteBufferWriter`), and everything that happens to these states after the load.

### Per-light contribution in Lighting64.dll (FUN_180009600, read by hand)
